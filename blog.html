Building Miffy's Sound World

by Kelly and Ceyda

Inspiration / How It Came About

Our project started from the Markov chain idea we learned about in class, but we did not want it to be just a basic probability demo. We wanted to make something more interactive and visually engaging for the user. Because of that, the project developed into a combination of a sequencer, a game, and a visual interface instead of only a grid of toggled notes.

One of the main questions behind the project was whether a probability based system could create something that felt engaging rather than just technically correct. A lot of generative music projects are interesting mathematically but can still feel repetitive or flat. We wanted this project to feel more playful and responsive, which is why we included elements like Miffy, different time of day moods, and the moving environment.

Visually, we also leaned into a retro desktop / Windows 95 look because we liked the contrast between cute pixel art and a more technical sequencer interface. That style made it possible for the project to feel both playful and computational at the same time, which fits what the music is doing.

High-Level Design

The project has three main parts: the sequencer, the WebAudio engine, and the game world. The sequencer manages the grids and harmony system, the audio engine generates the sounds and effects, and the game world turns the musical logic into interactive environments and events.

Grid A is the main pattern and always runs at 16 steps. Grid B is shorter by default at 13 steps, so it moves against Grid A instead of lining up perfectly each cycle. This creates interference patterns and gradual rhythmic changes over time, and we wanted the user to both hear and see that movement in the interface.

Implementation

In our implementation, the sequencer is built around six fixed musical rows defined in ROWS_CONFIG: kick, snare, hi-hat, clap, high melody, and low melody. We use it throughout the whole project for row colors, the platform zones in the game world, the type of sound each row triggers, and whether the row is treated as percussion or pitched material. So, the game, the grid, and the audio engine are all sharing the same row model instead of being separate.

The most clearly Markov part of the project is the chord engine. We store a set of chords in CHORDS, where each chord includes the pad tones, a high melody scale, and a low melody scale. Then we define a transition matrix in CHORD_TRANS. The function markovNextChord(i) samples the next chord by subtracting a random number through the weights in the current row. This means the harmony is not fully random. It moves according to the transition probabilities we wrote for each chord state.

Chord Markov Chain
const CHORD_TRANS=[
  [0.05,0.25,0.15,0.25,0.10,0.10,0.05,0.05],
  [0.30,0.05,0.10,0.10,0.05,0.20,0.10,0.10],
  [0.20,0.10,0.05,0.30,0.15,0.10,0.05,0.05],
  [0.35,0.15,0.10,0.05,0.10,0.10,0.10,0.05],
  [0.10,0.15,0.10,0.20,0.05,0.25,0.10,0.05],
  [0.15,0.20,0.05,0.15,0.15,0.05,0.15,0.10],
  [0.10,0.10,0.10,0.10,0.10,0.15,0.05,0.30],
  [0.30,0.10,0.15,0.15,0.10,0.10,0.05,0.05],
];
function markovNextChord(i){
  const w=CHORD_TRANS[i];
  let r=Math.random();
  for(let j=0;j<w.length;j++){
    r-=w[j];
    if(r<=0)return j;
  }
  return 0;
}

The rhythmic grid itself is implemented as two separate sequencers, gA and gB. Each grid stores four kinds of information per cell. Whether the cell is active, whether it is biased, what pitch it holds if it is melodic, and what velocity it should play with. We create those data structures in makeGrid(cols), give Grid A with a starting pattern and let Grid B start as a shorter pattern. That gives the system a recognizable musical base before the rhythm begins to shift.

Grid Data Structure
function makeGrid(cols){
  return {
    grid:Array.from({length:NROWS},()=>new Array(cols).fill(0)),
    biasGrid:Array.from({length:NROWS},()=>new Array(cols).fill(false)),
    pitchGrid:Array.from({length:NROWS},()=>new Array(cols).fill(null)),
    velGrid:Array.from({length:NROWS},()=>Array.from({length:cols},()=>.7+Math.random()*.5)),
    ph:0,
    cols
  };
}
let gA=makeGrid(COLS_A);
let gB=makeGrid(COLS_B);

The grid evolution rule is still probability-based, but it is not a strict Markov transition matrix like the chord system. Instead, each cell computes a probability of staying on or turning on based on its current state, the global controls, and its local neighborhood. In practice, this means density affects how full the pattern tends to become, repeat helps active notes persist, smooth lets neighboring cells influence one another, and chaos adds randomness so the pattern does not get stuck. This part of the implementation is closer to the cellular automata ideas than to a strict first-order Markov chain.

Probability-Based Grid Evolution
function evolveGrid(g){
  const{chaos,density,rep,smooth}=params,tod=getTODBlend();
  const effChaos=Math.max(0,Math.min(1,chaos+tod.chaosAdd+orbBoost*0.16));
  const effDensity=Math.max(0,Math.min(1,density+tod.densityAdd+orbBoost*0.12));
  g.grid=g.grid.map((row,r)=>row.map((cell,c)=>{
    const isPitched=ROWS_CONFIG[r].type==='pitched'; let bias=0;
    for(let br=Math.max(0,r-1);br<=Math.min(NROWS-1,r+1);br++)
      for(let bc=Math.max(0,c-1);bc<=Math.min(g.cols-1,c+1);bc++)
        if(g.biasGrid[br][bc])bias+=.12;
    bias=Math.min(bias,.4); const pull=rowPull[r]*.3;
    let p=cell?(isPitched?.6+rep*.2:.55+rep*.15):(isPitched?effDensity*.25:effDensity*.4);
    p+=bias+pull;
    const prev=(c-1+g.cols)%g.cols,next=(c+1)%g.cols,nb=(g.grid[r][prev]+g.grid[r][next])/2;
    if(cell)p=p*(1-smooth*.15)+smooth*.15*(nb>.5?.9:.1);
    p+=(Math.random()-.5)*effChaos;
    const nxt=Math.random()<Math.max(.02,Math.min(.97,p))?1:0;
    if(nxt&&!cell&&isPitched)assignPitch(g,r,c);
    if(nxt&&cell&&isPitched&&Math.random()<.15)assignPitch(g,r,c);
    return nxt;
  }));
}

The browser audio layer is implemented directly with WebAudio. We create an audio context and a low-pass filter. The drum voices use oscillators, filtered noise, gain envelopes, and parameter automation, while the melody uses fetched samples that are retuned to match the current chord.

WebAudio Setup And Control
function ac() {
  if (!AC) AC = new (window.AudioContext || window.webkitAudioContext)();
  return AC;
}

function output() {
  if (!masterGain) {
    masterGain = ac().createGain();
    limiter = ac().createDynamicsCompressor();
    underwaterFilter = ac().createBiquadFilter();
    underwaterLfo = ac().createOscillator();
    underwaterLfoGain = ac().createGain();
    masterGain.connect(underwaterFilter);
    underwaterFilter.connect(limiter);
    limiter.connect(ac().destination);
  }
  return masterGain;
}

Finally, the game world is not separate from the sequencer. The world uses the same row model through the ZONES array, which maps regions of the level to the kick, snare, hi-hat, clap, and melody rows. The player can walk and jump through those zones, switch the time of day, and collect remix orbs. When an orb is collected, applyOrbMusicalImpact(orb) advances the harmony, reassigns pitches, boosts coupling, and reshapes the pattern around the current playhead.

Challenges

One of the biggest challenges was making the system feel musical instead of arbitrary. If the probabilities were too loose, the pattern could collapse into noise. If they were too constrained, the piece stopped feeling alive. Controls like density, repeat, smooth, chaos, row pull, and coupling were all attempts to keep that balance.

Another challenge was the relationship between the two grids. Grid B being shorter than Grid A creates interference, but it also makes the project harder to reason about because different parts of the system can clash or drift apart. We had to add visual feedback so the user could see those relationships instead of only hearing them.

The interface itself was another challenge. There are status bars, control panels, two grids, a game screen, and an interference display all on one page. We spent a lot of time making it feel intentional rather than crowded.

What We Learned

This project made us understand more clearly that generative music is really about constraints. Randomness by itself is not enough. The meaningful part is deciding what should stay stable, what should evolve, and what kind of memory the system should have. In our project, that stability comes from row roles, chord scales, grid length, and the starting pattern.

We also learned that Markov ideas can be musically useful without needing the whole project to be a pure textbook Markov chain. Our chord progression is the cleanest Markov component, while the grid evolution is more of a probabilistic rule system. That hybrid ended up sounding better and feeling more expressive than a stricter implementation probably would have.

How To Use It / How It Works

To use the project, the user presses play to start the sequencer and audio system. Grid A and Grid B begin stepping forward, triggering drums, melodies, and pads based on the active cells. Users can edit the grids, adjust controls like tempo, chaos, density, and coupling, or randomize the patterns entirely.

The main interaction happens in Miffy's world, where the user moves through color coded zones connected to different sequencer rows. Floating remix orbs trigger musical changes like chord shifts and rhythm variations, while the time of day buttons change both the visuals and the overall mood of the music.

What We Are Proud Of

We are proud that the project became a full interactive composition environment instead of a small isolated demo. The sequencer, the WebAudio engine, the interface, and the game world all connect back to the same musical structure, which helps the whole project feel coherent rather than disconnected.

We are also proud that the ideas from class do not stay abstract. The Markov chord system becomes something the user can actually hear, while the interference patterns between the two grids become something the user can both hear and see in the interface. That connection between theory and interaction ended up being one of the strongest parts of the project.

Future Improvements

If we had more time, we would want to deepen the musical intelligence of the system. The current harmonic Markov chain works well, but it could become more nuanced with longer-term memory or row-specific transition behavior that still keeps the music coherent.

We would also like to expand the world interaction. Right now the game explains the music and triggers remix moments, but it could go further with collectible sound objects, more environmental zones, or platform behaviors that map directly onto rhythmic transformations.

Another future improvement would be clearer causal feedback. The interface already shows a lot, but it could go further in explaining exactly when a pattern changed because of time of day, row pull, coupling, orb influence, or automatic evolution. That would make the project stronger both as an instrument and as a teaching tool.
